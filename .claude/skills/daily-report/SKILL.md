# 일일 업무보고 자동화

하루치 Git/GitHub 활동을 수집해 **상사(상무)가 30초 안에 읽을 수 있는** 일일 업무보고서를
`reports/일일보고_YYYY-MM-DD.md` 로 저장한다.

## 핵심 원칙

1. **수집된 데이터에 없는 내용은 절대 쓰지 않는다.** 커밋 로그에서 근거를 찾을 수 없는
   성과·수치·일정은 추측해서 채우지 말고, 사용자에게 묻거나 빈칸으로 남긴다.
   보고서는 상사에게 그대로 올라간다 — 없는 사실이 한 줄 섞이면 보고서 전체의 신뢰를 잃는다.
2. **커밋 메시지를 그대로 옮기지 않는다.** `fix: null check in parser` 는 업무보고가 아니다.
   기술 로그를 **업무 언어**로 번역한다 (아래 4단계 참조).
3. **분량은 한 화면.** 완료 3~5줄, 진행 중 3줄 이내, 이슈는 있는 것만. 상세 근거는 부록에 접어둔다.

## 절차

### 1단계: 대상 날짜와 작성자 확정

- 날짜: 사용자가 명시하지 않으면 **오늘(KST)**. "어제 보고서" 같은 요청은 해당 날짜로 계산.
- 작성자: 기본값은 `git config user.email`. 이 값이 봇 계정(예: `noreply@anthropic.com`)이거나
  커밋이 0건으로 나오면, 작성자 필터를 바꿔 재수집하거나 필터 없이 전체를 훑어 사용자에게 확인한다.

### 2단계: 활동 수집

```bash
bash .claude/skills/daily-report/scripts/collect_git_activity.sh [YYYY-MM-DD] [작성자이메일]
```

- 출력: 커밋 목록(시각·메시지·변경 파일·통계), 미커밋 변경, 최근 브랜치 → 원시 로그(마크다운).
- 여러 저장소를 함께 보고할 때: `DAILY_REPORT_REPOS="/path/a:/path/b" bash ...`
- 원시 로그는 `_workspace/daily_YYYY-MM-DD_raw.md` 에 저장해두고 작업한다.

**GitHub 활동 보강(선택):** PR·리뷰·이슈가 업무의 큰 축이면 GitHub MCP 도구로 덧붙인다.
`search_pull_requests` (`author:<나> updated:YYYY-MM-DD`), `list_pull_requests`,
`issue_read`. 저장소 접근 범위 밖은 조회되지 않으니 실패하면 그냥 넘어간다.

### 3단계: 업무 단위로 묶기

커밋 1건 = 보고 1줄이 아니다. **같은 목적의 커밋들을 하나의 업무로 합친다.**

- 같은 파일군/브랜치/기능을 건드린 커밋 → 한 업무
- `fix typo`, `lint`, `rebase`, `wip` 같은 잡음 커밋 → 상위 업무에 흡수하거나 생략
- 변경량(+/-)과 파일 수로 업무의 무게를 판단한다. 5줄 수정과 500줄 신규 구현을 같은 비중으로 쓰지 않는다.
- 미커밋 변경 + 최근 브랜치는 "진행 중" 항목의 근거로 쓴다.

### 4단계: 업무 언어로 번역

| 기술 로그 | 업무보고 문장 |
|-----------|---------------|
| `fix: handle null in CSV parser` | 데이터 업로드 시 특정 파일에서 발생한 오류 수정 — 재발 방지 테스트 포함 |
| `refactor auth module (12 files)` | 로그인 모듈 구조 개선 — 후속 기능 개발 속도 확보 목적 |
| `add report PDF export` | 보고서 PDF 내려받기 기능 구현 완료 |

규칙:
- **결과와 영향**을 쓴다. 무엇을 했나가 아니라 무엇이 달라졌나.
- 내부 모듈명·함수명·라이브러리명은 지운다. 남겨야 한다면 괄호로 짧게.
- 근거 커밋 해시는 문장 끝 괄호에 남긴다 — 상사가 되묻거나 감사 대비용.
- 과대포장 금지. "완벽히 개선"이 아니라 "오류 수정 완료".

### 5단계: 보고서 작성

`templates/report_template.md` 구조를 따른다: ① 금일 완료 ② 진행 중 ③ 이슈·의사결정 요청
④ 익일 계획 ⑤ 부록(원시 로그, `<details>` 로 접기).

- **③ 이슈·의사결정 요청**은 상사가 판단·지원해야 하는 것만. 스스로 해결할 수 있는 건 넣지 않는다.
  없으면 "없음" 한 줄 — 억지로 만들지 않는다.
- **④ 익일 계획**은 미커밋 변경·미완 브랜치에서 도출한다. 근거가 없으면 사용자에게 한 줄 묻는다.
- 저장: `reports/일일보고_YYYY-MM-DD.md` (없으면 `reports/` 생성). 같은 파일이 이미 있으면
  덮어쓰기 전에 사용자에게 확인한다.

### 6단계: 자체 검증 후 보고

저장 전 다음을 직접 확인하고, 걸리는 게 있으면 고친다.

- [ ] 모든 완료 항목에 근거 커밋이 있는가? (없는 항목은 삭제하거나 사용자에게 확인)
- [ ] 커밋 메시지를 그대로 복사한 문장이 남아 있지 않은가?
- [ ] 상사가 모를 내부 용어가 남아 있지 않은가?
- [ ] 완료 3~5줄 / 한 화면 분량을 지켰는가?
- [ ] 커밋 0건인데 완료 업무가 채워져 있지 않은가? (그 경우 사용자에게 물어 채운다)

작업이 끝나면 사용자에게 **파일 경로 + 완료 업무 요약 3줄**을 보여주고, 사실과 다른 부분이
있으면 알려달라고 한다. 커밋은 사용자가 요청할 때만 한다.

## 커밋이 0건일 때

회의·문서 작업·비개발 업무만 있던 날은 정상이다. 없는 내용을 지어내지 말고,
"오늘 커밋 활동이 없습니다. 회의·검토 등 진행하신 업무를 한 줄씩 알려주시면 보고서 문체로
정리하겠습니다" 라고 사용자에게 묻는다.

## 주간 요약 요청 시

`reports/일일보고_*.md` 를 해당 주 범위로 읽어 합친다. 일일보고를 다시 수집하지 말고
이미 저장된 파일을 근거로 쓴다 — 매일 검증된 내용이므로 더 신뢰할 수 있다.
